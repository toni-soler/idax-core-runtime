# IDAX Core runtime 0.5.0

- Private source revision: `b0d6530db125687027e8bc258fcf9f234029429b`
- Binary SHA-256: `aba51de07dba9e336c724ccdabc3696dc4255bf5821ed689dee9287aacc08d0a`
- Published artifact: `es.idynamicsax.idax:idax-core:0.5.0`

The binary is distributed under the IDAX Core Runtime Binary License. Source
JARs, Javadocs, generators and `idax-legacy` are intentionally excluded.

This increment is the 0.4.0 runtime plus two security changes and nothing else.
It ships no database migration: the 91 Core migrations are unchanged.

- **Per-operation approval.** An authenticated user confirms one specific
  operation with a fresh authenticator code and receives a short-lived approval
  bound to the user, tenant, action, resource and intent digest. The service
  that executes the operation verifies it (`OperationApprovalVerifier`, public
  verification material only) and consumes it once. Issuance
  (`OperationApprovalService`) claims the TOTP time-step through the same
  atomic capability sign-in uses, accepts no recovery codes and has no
  superuser or service bypass. Lifetime: `idax.security.operation-approval.expiration-seconds`
  (default 120, capped at 300).
- **Only access tokens are bearer sessions.** `LocalTokenValidator` now rejects
  any token whose `type` claim is present and is not `access`. Resource servers
  that call the validator from their own filter previously accepted a refresh
  token as a session. Tokens without a `type` claim are still accepted.

Compatibility: additive for applications built against 0.4.0. Applications that
component-scan `es.idynamicsax.idax.security` and `es.idynamicsax.idax.service.auth`
gain the issuer beans and therefore need the LOCAL signing key they already
need for sign-in; resource servers import `OperationApprovalVerifier` explicitly.
